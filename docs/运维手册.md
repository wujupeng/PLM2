# PLM2 详细运维手册

本文面向开发、测试和生产运维人员，说明当前仓库结构下的构建、部署、运行、监控、备份及故障处理。生产上线前应将本文中的示例地址、账号、目录、备份保留期和服务等级替换为经批准的环境值。

## 1. 运行架构与端口

| 组件 | 工程位置 | 默认端口/路径 | 说明 |
| --- | --- | --- | --- |
| Web 前端 | `plm-frontend/` | Vite 开发端口 `3000`；生产为静态资源 | 开发代理 `/api` 到网关 `8080`；生产 Web 服务器也需配置该反向代理 |
| API 网关 | `plm-backend/plm-gateway/` | `8080` | 前端统一 API 入口，路由默认将多个 API 前缀转发至 `plm-system` |
| 系统服务 | `plm-backend/plm-system/` | `8082` | 身份、系统管理及当前聚合工程中的业务控制器；生产使用 PostgreSQL |
| 数据库 | 外部基础设施 | PostgreSQL 默认连接 `5432` | 生产必须使用独立持久化数据库 |
| Redis | 外部基础设施 | 本地测试默认 `127.0.0.1:6381`；其他环境由配置指定 | 网关限流依赖 Redis；本地测试 Redis 使用独立认证、RDB/AOF 持久化目录 |
| Nacos | 外部基础设施（如采用） | bootstrap 默认 `localhost:8848` | 网关 bootstrap 配置包含 Nacos 地址/命名空间设置；服务发现路由需要相应服务注册和可用配置 |

当前根 `pom.xml` 聚合模块是 `plm-common`、`plm-gateway`、`plm-system`。网关中存在 `lb://...` 服务路由；若目标业务服务没有部署、注册或正确配置，这些业务路由不可用。上线前应核对本次发布实际交付的服务清单，不要仅凭前端菜单判断服务已就绪。

## 2. 环境要求

### 构建机

- Java 17（后端 POM 以 Java 17 为目标）
- Maven 3.8 或更高版本
- Node.js 20 LTS 和 npm（前端）
- 能访问 Maven/npm 依赖仓库

### 运行环境

- PostgreSQL 生产实例和独立应用账号
- Java 17 运行时
- 网关/系统服务之间的网络连通性
- 可持久化、可备份的文档及邮件附件目录
- 按生产配置要求提供 Redis、Nacos 及其他已部署业务服务
- 反向代理或负载均衡器提供 HTTPS，并将 `/api` 转发至网关

开发 `dev` profile 默认使用 PostgreSQL 兼容模式的文件 H2，开发启动脚本将数据库放在仓库 Git 忽略目录 `.local/dev-h2/`，服务重启后数据保留。文件 H2 仅作本机过渡联调，不满足生产或最终持久化验收；生产不得使用 H2。

## 3. 配置清单

通过受控的环境变量或密钥管理系统提供配置。Spring Boot 环境变量可覆盖 YAML 中的默认属性。

### 系统服务

| 环境变量 | 用途 | 生产要求 |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | 激活运行 profile | 设为 `prod` |
| `PLM_DB_URL` | PostgreSQL JDBC 地址 | 指向生产数据库；使用 TLS/私网连接策略 |
| `PLM_DB_USERNAME` | 数据库账号 | 使用最小权限的专用账号 |
| `PLM_DB_PASSWORD` | 数据库密码 | 从密钥管理系统注入，不写入仓库或命令历史 |
| `PLM_DB_POOL_SIZE` | Hikari 最大连接数 | 根据数据库连接上限、实例数和并发压测结果设置 |
| `PLM_JWT_SECRET` | JWT 签名密钥 | 生产必设；使用强随机高熵值，所有需要验证同一令牌的服务保持一致 |
| `SERVER_PORT` | Spring Boot 服务端口 | 默认 `8082`，仅在端口规划需要时调整 |

示例（仅展示变量名称，不包含实际凭据）：

```bash
export SPRING_PROFILES_ACTIVE=prod
export PLM_DB_URL='jdbc:postgresql://<db-host>:5432/<database>?sslmode=require'
export PLM_DB_USERNAME='<application-user>'
export PLM_DB_PASSWORD='<inject-from-secret-manager>'
export PLM_DB_POOL_SIZE='20'
export PLM_JWT_SECRET='<inject-a-long-random-secret>'
```

### API 网关

| 环境变量/属性 | 用途 | 当前默认值 |
| --- | --- | --- |
| `PLM_SYSTEM_URI` | 网关转发到系统服务的基础地址 | `http://localhost:8082` |
| `PLM_REDIS_HOST` | 网关 Redis 主机 | 本地 `127.0.0.1` |
| `PLM_REDIS_PORT` | 网关 Redis 端口 | 本地 `6381` |
| `PLM_REDIS_PASSWORD` | 网关 Redis 认证密码 | 本地脚本生成并存放于 `.local/redis-test/password`；其他环境由密钥管理系统注入 |
| `PLM_REDIS_DATABASE` | Redis 数据库编号 | `0` |
| `PLM_REDIS_TIMEOUT` | Redis 命令超时 | `3s` |
| `PLM_REDIS_CONNECT_TIMEOUT` | Redis 建连超时 | `3s` |
| `PLM_REDIS_POOL_MAX_ACTIVE` | 最大活动连接数 | `16` |
| `PLM_REDIS_POOL_MAX_IDLE` | 最大空闲连接数 | `8` |
| `PLM_REDIS_POOL_MIN_IDLE` | 最小空闲连接数 | `1` |
| `PLM_REDIS_POOL_MAX_WAIT` | 连接池等待上限 | `3s` |
| `NACOS_ADDR` | bootstrap 中 Nacos 地址 | `localhost:8848` |
| `NACOS_NAMESPACE` | bootstrap 中 Nacos 命名空间 | `plm-dev` |
| `SERVER_PORT` | 网关端口 | `8080` |
| `PLM_JWT_SECRET` | 网关 JWT 相关配置的环境覆盖项 | 不要使用开发默认值 |

Nacos 配置、服务注册与发现的实际行为取决于交付环境中的依赖和服务注册情况。请先核对构建包及环境配置，再决定是否启用 Nacos；不要仅因 `bootstrap.yml` 存在就假定服务已自动注册。

### 本地测试 Redis

仓库提供 `scripts/test-redis.sh` 管理专用本机测试 Redis。脚本固定绑定 `127.0.0.1`，默认使用端口 `6381`，启用 requirepass、RDB 快照和 AOF；数据、配置、日志及自动生成的 256-bit 测试密码保存在 Git 忽略的 `.local/redis-test/`，不会连接或替换 `6379` 上的其他实例。第一次启动需有本机 `redis-server`、`redis-cli`、`nc` 和 `openssl`：

```bash
bash scripts/test-redis.sh start
export PLM_REDIS_PASSWORD="$(<.local/redis-test/password)"
```

使用上述环境变量启动 Gateway，使应用连接到该测试 Redis。重新打开终端后，按同一方式读取本地密码文件再启动 Gateway。检查状态和停止服务：

```bash
bash scripts/test-redis.sh status
bash scripts/test-redis.sh stop
```

停止只会通过认证并校验 PID/配置后关闭由本脚本管理的 Redis 进程，保留数据目录。若目标端口被其他 Redis 占用、认证不匹配或 PID 不可核验，脚本会拒绝接管/停止。其他环境必须通过 `PLM_REDIS_*` 配置注入 Redis 主机、端口、凭据、数据库编号和超时；生产凭据不得放入本地测试目录或 Git。

### 隔离测试账号初始化

仅用于 `localhost:8082` 的开发 H2 实例；脚本会检查 health 为 `UP` 且数据库类型为 H2，并拒绝非 loopback 目标。默认文件 H2 在服务重启后保留测试数据；只有明确决定重建隔离种子库时才重新轮换账号并 provisioning。

首次启动系统服务前，若 `.env.local` 不存在，先在仓库根目录生成本地 JWT 密钥（不要覆盖已有文件）。`scripts/start-dev.sh` 会自动加载此文件；手动启动时再于同一终端加载：

```bash
if [ ! -e .env.local ]; then
  umask 077
  printf 'PLM_JWT_SECRET=%s\n' "$(openssl rand -hex 64)" > .env.local
  chmod 600 .env.local
else
  printf '.env.local exists; preserving it.\n'
fi
set -a
. ./.env.local
set +a
```

确认 `curl --fail http://localhost:8082/actuator/health` 显示 `UP` 且数据库为 H2。用无回显输入提供当前隔离实例已知的初始管理员密码，然后通过应用 API 轮换密码并生成其余本机随机凭据：

```bash
read -s -r -p 'Initial local admin password: ' PLM_BOOTSTRAP_INITIAL_PASSWORD
printf '\n'
export PLM_BOOTSTRAP_INITIAL_PASSWORD
export PLM_TEST_BOOTSTRAP_CONFIRM=isolated-dev-h2
export PLM_DATASOURCE_URL="jdbc:h2:file:$PWD/.local/dev-h2/plm_system;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE;DB_CLOSE_ON_EXIT=FALSE"
node scripts/bootstrap-dev-admin.mjs
unset PLM_BOOTSTRAP_INITIAL_PASSWORD PLM_TEST_BOOTSTRAP_CONFIRM PLM_DATASOURCE_URL
```

首次初始化使用 `PLM_TEST_BOOTSTRAP_CONFIRM=isolated-dev-h2`。若本机凭据已经存在，默认拒绝覆盖；只有在确认目标为可丢弃的隔离开发文件 H2、并决定重建全部测试账号时，才使用 `isolated-dev-h2-reset`。脚本会保留已有随机 JWT 密钥，安全替换其管理的测试凭据，写入权限为 `0600` 的 `.env.local` 且不输出凭据。初始化测试数据时：

```bash
set -a
. ./.env.local
set +a
export PLM_TEST_RUN_ID="AF1000-$(date +%Y%m%d%H%M)-$(openssl rand -hex 4)"
node tests/seed/provision-dev.mjs
node scripts/seed-af1000-permissions.mjs
```

同一个 `PLM_TEST_RUN_ID` 必须贯穿 provision 与角色授权步骤。种子脚本通过系统 REST API 创建唯一编码的公司、11 个部门、测试角色和 14 个测试账号，并逐个验证登录；角色授权脚本按[AF1000 测试岗位权限矩阵 v1](../reports/18-permission-matrix.md)再经系统 API 授予最小权限并读回核对；均不直接写数据库。登录成功或权限写入成功都不能单独当作业务闭环验收。`.env.local` 与 `.local/redis-test/`、`.local/dev-h2/` 均为本机敏感/测试数据，严禁提交或共享。

若测试 H2 需要重启保持验证，先用应用 API 建立一条唯一测试标记，安全停止并再次启动 system，再以认证 API 读回该标记；不要用删除文件代替持久化测试。

### 前端反向代理

生产前端默认请求同源 `/api`。Web 服务器应将 `/api/` 路径转发到网关，并保留必要的请求头、请求方法、查询参数和超时设置。示例 Nginx 片段：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/api/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 5s;
    proxy_read_timeout 60s;
}
```

HTTPS 证书、静态资源缓存策略、访问日志和请求体大小限制由实际使用的 Web 服务器/负载均衡配置负责。网关配置默认请求体上限为 50 MiB；系统服务 Servlet multipart 配置为单文件 50 MiB、单请求 100 MiB，业务配置项还可能进一步限制上传大小。

## 4. 构建和发布

### 4.1 获取代码及构建

```bash
git clone https://github.com/wujupeng/PLM2.git
cd PLM2

bash scripts/build-versioned.sh
```

版本化脚本从 Git HEAD 读取短 commit ID，并同时构建 Gateway、system 和前端；工作区不干净时 commit 字段带 `-dirty` 标识。system/Gateway 的 `/actuator/info` 应返回非空应用名、版本、构建时间和 Git commit；前端主布局页脚显示相同版本信息。发布应使用已提交、干净且有标签的源码构建，不应以 `unknown` 或 `-dirty` 制品发布。若单独运行 Maven，使用 `-Dplm.git.commit=<commit>` 注入 Git commit。

发布前记录 Git commit、构建时间、依赖版本和制品校验和。不要将 `target/`、`node_modules/` 或运行时 `data/` 上传为发布源码。

典型制品位置：

- `plm-backend/plm-gateway/target/plm-gateway-1.0.0-SNAPSHOT.jar`
- `plm-backend/plm-system/target/plm-system-1.0.0-SNAPSHOT.jar`
- `plm-frontend/dist/`

快照版本只适合作为本仓库当前的构建示例；正式发布应采用组织批准的版本标识和制品仓库，不要仅靠覆盖文件来识别版本。

### 4.2 数据库准备

1. 创建生产 PostgreSQL 数据库和专用应用账号，按最小权限原则授予访问该数据库及 Flyway 迁移所需对象的权限。
2. 网络策略只允许应用服务访问数据库端口，限制管理端来源。
3. 配置连接地址、账号和密码；确认连接池总连接数不超过数据库可用连接数。
4. 初次部署前验证目标数据库为空或已处于受支持的迁移状态，并先完成备份。

生产 `prod` profile 会连接 PostgreSQL，并启用 Flyway；系统服务启动时会执行尚未应用的迁移。仓库已有连续演进的 SQL 迁移，生产升级前须在预生产数据库副本上验证。

#### 本机/隔离环境迁移验证

仓库提供 `docker-compose.postgres.yml`（PostgreSQL 16）和 `scripts/verify-postgres-migrations.sh`。Docker 模式仅绑定 `127.0.0.1`，使用独立命名卷；在受控本机环境提供 `PLM_POSTGRES_PASSWORD` 与 `PLM_JWT_SECRET` 后执行：

```bash
set -a
. ./.env.local
set +a
read -s -r -p 'Local PostgreSQL test password: ' PLM_POSTGRES_PASSWORD
printf '\n'
export PLM_POSTGRES_PASSWORD
bash scripts/verify-postgres-migrations.sh
unset PLM_POSTGRES_PASSWORD
```

Docker 缺失但本机 PostgreSQL 已安装、启动且测试数据库/账号已创建时，可用 `PLM_POSTGRES_USE_DOCKER=false` 让同一脚本通过 `psql` 检查 Flyway 版本、表数量和服务 health。两种模式只用于隔离测试，不是生产部署步骤。迁移脚本当前验证 Flyway 版本 173；增加数据库迁移后，应同步更新验证目标和测试记录。

### 4.3 启动服务

示例为前台运行，适用于验证启动参数。生产建议使用 systemd、容器平台或组织标准进程管理工具，配置自动重启、资源限制、日志采集和健康探针。

```bash
# 在 plm-backend 目录执行；请先按环境注入数据库和 JWT 变量
SPRING_PROFILES_ACTIVE=prod \
PLM_DB_URL='jdbc:postgresql://<db-host>:5432/<database>?sslmode=require' \
PLM_DB_USERNAME='<application-user>' \
PLM_DB_PASSWORD='<secret>' \
PLM_JWT_SECRET='<secret>' \
java -jar plm-system/target/plm-system-1.0.0-SNAPSHOT.jar
```

另一个终端启动网关：

```bash
# 按部署拓扑替换地址，并从密钥系统注入实际 JWT 密钥
PLM_SYSTEM_URI='http://<system-service-host>:8082' \
PLM_JWT_SECRET='<same-secret-as-required-by-token-validation>' \
java -jar plm-gateway/target/plm-gateway-1.0.0-SNAPSHOT.jar
```

生产不应把密码直接写在 shell 历史、命令行参数、脚本仓库或进程列表可见的启动命令中；以上占位符仅用于说明。使用权限受控的环境文件、密钥挂载或密钥管理服务，并限制文件读取权限。

### 4.4 发布前检查

- 已在预生产环境以同版本制品完成启动、登录、关键业务 API 和文件上传/下载验证。
- 数据库迁移在备份后的副本执行成功，无未审阅的 SQL 变更。
- 反向代理 `/api` 路由、HTTPS、DNS 和防火墙策略已验证。
- JWT 密钥、数据库凭据和外部集成密钥已经从可信密钥源注入。
- 文档/附件持久目录已创建，服务用户有适当读写权限，空间和 inode 监控已就绪。
- 网关及系统服务的健康检查已通过。
- 已明确回滚策略、变更负责人、维护窗口和恢复联系人。

## 5. 日常运行

### 5.1 启动/停止顺序

建议启动顺序：

1. PostgreSQL 及已启用的基础依赖。
2. 系统服务，等待 Flyway 完成并检查健康状态。
3. 网关及所需的其他业务服务。
4. 前端静态资源或 Web 服务入口。

停止时先从负载均衡摘除流量，等待在途请求完成，再停止网关和业务服务，最后按数据库维护规程处理基础设施。不要在迁移执行中强制终止系统服务。

### 5.2 健康检查

```bash
curl -fsS http://127.0.0.1:8082/actuator/health
curl -fsS http://127.0.0.1:8080/actuator/health
```

将探针配置为有超时和有限重试的 HTTP GET。若应用暴露了依赖状态，应同时检查数据库、Redis（若启用）和下游服务连通性。健康端点不通过时不要仅通过重启掩盖问题，先检查日志、连接池和依赖状态。

系统服务 Actuator 当前暴露 `health`、`info`，并配置了 `show-details: always`；网关暴露 `health`、`info`、`prometheus`、`gateway`。生产必须通过网络边界限制管理端点访问，尤其不要将网关路由详情和健康依赖信息开放给公网。

### 5.3 日志

- 后端使用 Spring Boot 日志配置，业务包默认 `INFO`；开发 profile 可出现更详细日志。
- 生产日志应交由 systemd/journald、容器日志驱动或集中式日志平台采集，设置保留期和轮转上限。
- 统一记录发布版本、实例、时间戳、请求追踪标识和错误堆栈；避免记录密码、JWT、个人敏感信息或文档内容。
- 故障排查优先关联网关和系统服务同一时间段的日志、Trace ID、HTTP 状态码及数据库迁移记录。

### 5.4 资源与容量

持续监控 CPU、堆内存、GC、线程、磁盘、数据库连接池、数据库连接/锁/慢查询、Redis 可用性、接口错误率和延迟。

数据库连接池默认最大连接数为 20、最小空闲连接为 5；调整前应按应用实例数计算最大连接总量，并与数据库连接上限及其他客户端预留量共同评估。网关应用本身设置了默认限流配置；生产阈值应通过压测、业务需求和共享实例数进行验证。

文件上传的容器限制与业务配置必须协调：单文件最大值不能超过 Servlet 50 MiB 上限，请求总大小不能超过 100 MiB；业务配置 `oa.doc.upload.max.size.mb`、`oa.mail.attachment.max.size.mb` 还可能设置更低值。

### 5.5 G9-N4 未结业务迁移（T079）

迁移批次的数据导入采用标准化 JSON 行，与现有 BOM 导入 API 的 JSON 行处理方式一致；系统不直接解析旧系统的 CSV/Excel。由旧系统导出或转换出的数据需按当前 ERP 保存请求字段整理。

1. 在“数据迁移 → 未结业务迁移 → 同步批次”创建批次。销售/采购订单、委外单、生产工单、待检业务分别使用对应对象类型；采购和销售在途使用“在途”批次；应收、应付和委外结算使用“未结算业务”批次。
2. 在批次行操作中提交 JSON。单次最多 1,000 条，单条 `payload` 最大 1 MiB。订单、到货和发运记录必须包含 `header` 与至少一条 `lines`；单据头和行字段参照相应 ERP 保存请求 DTO。
3. 后端逐行进行必填校验、对象类型匹配和批次内来源单号去重。有效行进入“待审核”，无效行保留在批次中并显示校验失败原因，方便审计与重新导入。
4. 业务人员查看来源数据后逐行审核。只有审核通过的行可以“转正式单据”；该操作调用现有 ERP 服务创建正式单据头和明细。单行创建在事务中完成；失败行会记录原因并可重试。若来源数据需修改，可先关闭失败行，再在新批次修正后重新导入。
5. 已包含暂存行的批次不可编辑或删除。批次统计显示暂存总数、已转正式数、失败/驳回数及待审核状态。

批次导入请求示例（以未结销售订单为例）：

```json
{
  "sourceFile": "legacy-open-orders.json",
  "records": [
    {
      "sourceNo": "OLD-SO-0001",
      "objectType": "OPEN_SALES_ORDER",
      "payload": {
        "header": {
          "orderNo": "SO-2026-0001",
          "customerCode": "CUST-001",
          "orderStatus": "OPEN"
        },
        "lines": [
          {
            "materialCode": "MAT-001",
            "uom": "PCS",
            "orderQty": 10,
            "deliveredQty": 2,
            "remainingQty": 8
          }
        ]
      }
    }
  ]
}
```

后端 API（前端经由网关 `/api` 前缀访问）：

- `POST /api/mig/open-business/batches/{batchId}/rows/import`：暂存 JSON 行并返回逐行校验结果。
- `GET /api/mig/open-business/batches/{batchId}/rows`：分页查看暂存数据和审核/转换状态。
- `POST /api/mig/open-business/batches/rows/{rowId}/review`：提交审核结论，例如 `{"approved":true,"comment":"核对通过"}`。
- `POST /api/mig/open-business/batches/rows/{rowId}/promote`：将审核通过的行写入正式 ERP 单据，响应包含目标记录 ID。

导入接口当前按现有 ERP DTO 字段校验标准化 JSON；如旧系统字段不同，需在导入前完成字段转换。字段映射页用于登记迁移规则，本导入接口当前不自动执行自定义转换表达式。每次切换前仍须按本手册第 7 节完成备份、全量/增量演练、差异对账及回退验证。

## 6. 数据库迁移和版本升级

### 6.1 Flyway 管理

- 迁移脚本位于 `plm-backend/plm-system/src/main/resources/db/migration/`，命名遵循 `V<版本>__<描述>.sql`。
- 系统服务启动时自动执行待处理迁移，迁移历史保存在 Flyway 管理表中。
- 已在任一环境执行的迁移文件不得原地修改、删除或重命名；新增结构变更应追加新的版本文件。
- `baseline-on-migrate` 已配置启用；将已有数据库纳入管理前，应先确认基线版本和现存结构，禁止对不明状态数据库直接启动生产服务。
- `prod` profile 禁用 Flyway clean。不要在生产执行 `flyway clean`、手工删除迁移历史或绕过校验。

### 6.2 推荐升级流程

1. 变更评审 SQL、兼容性、索引策略、锁表影响、预计耗时及应用新旧版本兼容性。
2. 对生产数据库和文件存储完成备份，并验证备份文件可读取。
3. 将近期生产数据恢复到隔离的预生产环境，运行新版本并验证迁移及关键流程。
4. 在维护窗口停止或摘除写流量，按应用与数据库升级顺序执行变更。
5. 启动新系统服务，检查迁移日志和健康状态；再启动/放行网关流量。
6. 执行登录、核心查询/写入、附件访问和外部集成冒烟测试。
7. 监控错误率、延迟、数据库连接和文件系统容量，确认稳定后结束窗口。

应用回滚不一定等于数据库可回滚。若新版本已应用不可逆迁移，按预先演练的数据恢复或向前修复方案处理；不要仅回退 JAR 并假定数据库自动恢复。

## 7. 备份与恢复

### 7.1 必须纳入备份的数据

1. PostgreSQL 业务数据库及 Flyway 迁移历史。
2. 系统服务工作目录下的文档与邮件附件文件。默认路径包括：
   - `./data/oa-documents`
   - `./data/oa-mail-attachments`
3. 如部署采用对象存储、独立文件挂载或外部系统，还需按其自身策略备份配置及对象数据。
4. 版本化部署制品、运行配置（不含明文秘密）和数据库恢复说明。

相对路径以系统服务进程的工作目录为基准。生产应将数据目录映射到明确的持久卷或受管存储，并固定服务启动工作目录；不要把唯一副本放在临时容器可写层。

### 7.2 PostgreSQL 备份示例

使用 PostgreSQL 官方客户端，并通过受控的 `.pgpass`、密钥注入或云数据库备份机制提供认证；不要把密码直接拼接到命令行。

```bash
pg_dump --format=custom \
  --host='<db-host>' --username='<backup-user>' \
  --dbname='<database>' \
  --file='plm-$(date +%Y%m%d-%H%M%S).dump'
```

还应根据数据库规模和恢复目标配置 WAL/PITR 或云数据库自动备份。备份任务成功不代表恢复可用；定期在隔离环境进行恢复演练，并记录实际恢复时间、数据时间点和验证结果。

### 7.3 文件数据备份示例

以下示例假定已确认源目录、目标介质、权限和一致性窗口；生产可替换为对象存储快照或存储平台备份。

```bash
rsync -aH --numeric-ids \
  /srv/plm/data/ \
  /mnt/backup/plm-data/
```

具体目录应与 `oa.doc.storage.dir` 配置及邮件附件服务实际使用路径核对。对同一时间点要求严格一致的恢复点，应协调暂停写入或使用文件系统快照，并与数据库备份关联记录。

### 7.4 恢复原则

1. 先选择正确的目标环境和恢复时间点，审批后在隔离环境演练。
2. 对数据库和文件存储使用同一恢复点；校验文件数量、大小、权限以及业务引用关系。
3. 先恢复数据库到专用目标库，再恢复文件数据到正确的数据目录；确认密钥、文件挂载和服务账号权限。
4. 通过应用健康检查、登录、文档/附件下载和关键业务校验后，再切换流量。
5. 保留当前故障现场副本，记录恢复操作和差异；未确认前不要覆盖现有数据。

组织应为每个环境定义 RPO、RTO、保留周期、加密方式、异地副本和恢复审批人；本仓库不规定统一数值。

## 8. 安全基线

- 对外统一使用 HTTPS；PostgreSQL、Redis、Nacos 和服务间流量应置于受控网络，按环境启用传输加密。
- 生产设置强随机 `PLM_JWT_SECRET`，由授权主体管理和轮换；轮换会影响已有令牌，应安排兼容或重新登录策略。
- 数据库服务账号实行最小权限，运维账号与应用账号分离。
- 生产默认配置中的开发密钥不能作为生产凭据；所有密钥都应从 Git 和普通日志中隔离。
- Actuator、H2 Console、Nacos 控制台和数据库管理端不得直接暴露公网。H2 Console 仅为本地开发配置启用。
- 将上传文件存储在服务专用目录或对象存储中，配置最小文件系统权限、容量告警、恶意文件检查策略和访问审计。
- 按企业策略执行依赖漏洞扫描、代码审查、镜像/制品签名、备份加密和日志保留。

## 9. 故障排查

| 现象 | 检查项 | 处置建议 |
| --- | --- | --- |
| 前端页面正常但 API 报网络错误/502 | Web 服务器 `/api` 代理；网关端口；网关日志 | 检查反向代理目标、网关进程和端口连通性 |
| 网关转发返回 502/504 | `PLM_SYSTEM_URI`、系统服务健康状态、防火墙、连接超时 | 从网关主机直接检查系统服务健康端点与网络策略 |
| 某些菜单路由不可用 | 是否存在对应服务制品；`lb://` 服务是否注册；Nacos/发现配置 | 对照本次交付的服务清单与注册状态，不要把无服务实例误判为系统服务故障 |
| 系统服务无法启动 | 数据库 DNS/路由/凭据/权限；Flyway 错误；端口占用；Java 版本 | 查看启动日志首个根因，验证数据库连接及迁移状态后再重启 |
| 数据库迁移失败 | Flyway 历史、SQL 错误、锁和数据库版本 | 暂停发布并保留日志/数据库快照；评审修复迁移，不要手工删历史记录 |
| 登录失败或令牌验证失败 | 两端 JWT 密钥是否一致；时间同步；令牌过期；用户/权限数据 | 核对密钥注入与时钟，不要在日志或工单中粘贴完整令牌 |
| 上传失败/413/文件不存在 | 代理请求体限制、网关 50 MiB 限制、Servlet 50/100 MiB 限制、业务配置、目录权限/磁盘空间 | 逐层协调上传上限；检查文件存储挂载及服务用户权限 |
| 数据库连接耗尽 | 实例数、连接池大小、慢查询、连接泄漏、数据库连接上限 | 计算所有应用实例的最大连接总和，定位长事务/慢查询后再调池 |
| Redis 相关网关功能异常 | Redis 地址、端口、认证/TLS、网络策略及服务状态 | 对照目标环境检查连接；确认受影响的功能是否依赖 Redis |

故障工单至少记录发生/恢复时间、影响范围、发布版本、相关 Trace ID、脱敏后的错误信息、处置动作及数据恢复情况。

## 10. 定期维护清单

### 每日

- 检查服务健康状态、错误率、延迟、磁盘容量和数据库可用性。
- 检查数据库与文件备份任务结果及失败告警。
- 检查关键外部集成的接口错误、积压、失败批次和补偿队列。

### 每周

- 抽查备份完整性和文件存储容量增长。
- 审阅数据库慢查询、连接池、异常登录和高错误率日志。
- 检查待处理迁移、接口失败及人工补偿任务。

### 每月/每次发布前

- 在隔离环境演练数据库及文件恢复。
- 审阅依赖安全更新、账号权限、密钥轮换计划和公网暴露面。
- 验证预生产升级、数据库迁移、关键业务流程和回滚/前滚方案。
- 核对数据库、文件存储、应用制品和配置的版本及恢复关联关系。

## 11. 支持与变更记录

每次上线应记录：变更单号、发布 commit/制品版本、部署环境、数据库迁移版本、配置变更（不包含秘密）、操作者、开始/结束时间、健康检查结果、回滚决策和遗留问题。
